# Dev Environment Bootstrap — Design

**Date:** 2026-06-02
**Status:** Approved (brainstorm complete; implementation plan pending)
**Owner:** Daniel Mortensen

## Summary

A chezmoi-based bootstrap and ongoing-sync system for a developer Mac. One command on a fresh machine clones a public dotfiles repo, prompts for machine type (work or home), and walks an ordered set of scripts that install tools, pull secrets from 1Password, configure editors, and clone the OVO repos. The same tool keeps two machines in sync day-to-day.

## Goals

- **Full machine bootstrap.** Fresh macOS → fully working dev environment from a single command, with the minimum possible interactive steps.
- **Dual-machine portability.** Same repo drives both the work and home machine, with per-machine variance handled cleanly.
- **Ongoing sync, not just bootstrap.** Day-to-day dotfile edits propagate between machines through the same tool.
- **Repeatable and idempotent.** Re-running is always safe and resumes from any failure point.
- **Documented by construction.** The repo is itself the runbook; no separate "how to set up your machine" wiki page.

## Non-goals

- Cross-OS support (macOS only).
- CI/automated VM testing. Local checks + occasional scratch-user verification.
- Backwards-compatibility with a previous setup (greenfield).
- Insulating against chezmoi disappearing. If that ever happens, a future agent can extract logic to plain shell scripts at the cost of a few hours.

## Constraints and decisions

| Decision | Choice | Reasoning |
|---|---|---|
| Tool | chezmoi, used natively | Single tool for templating, ordered scripts, secrets, sync. Designing around it (thin-wrapper variant) sacrificed too much of its value for a low-probability risk. |
| Secrets backbone | 1Password CLI (`op`) | User already uses 1Password; one master account works across machines; SSH/GPG/tokens centralised. |
| Secret access pattern | `op read` inside `run_*` scripts, **never** `onepasswordRead` in dotfile templates | Avoids bootstrap chicken-and-egg (template rendering happens before 1Password is signed in). Keeps secrets out of rendered intermediate files. |
| Machine identification | First-run prompt → `~/.config/chezmoi/chezmoi.toml` | Survives renames, no env-var discipline required, easy to override. |
| Repo visibility | Public personal GitHub repo | No auth needed before clone (breaks chicken-and-egg). All secrets stay in 1Password; nothing identifying in git. |
| Lifecycle | Bootstrap + ongoing sync via the same tool | chezmoi is designed for both; no reason to split. |
| Test strategy | Local `chezmoi diff` + shellcheck + occasional scratch macOS user | macOS CI runners are slow and don't validate the "second run" case that `run_onchange_*` exists for. |

## Architecture

### Repository layout

```
~/.local/share/chezmoi/                         (canonical chezmoi source dir)
├── .chezmoi.toml.tmpl                          first-run prompts (machine type)
├── .chezmoidata/                               YAML data, auto-loaded into templates
│   ├── packages.yaml                           brew formulae + casks + mas apps
│   ├── vscode-extensions.yaml                  VSCode extension IDs
│   ├── repos.yaml                              OVO repos to clone
│   ├── mcps.yaml                               MCP servers to register
│   └── mise.yaml                               global mise tools
│
├── dot_zshrc.tmpl                              → ~/.zshrc
├── dot_gitconfig.tmpl                          → ~/.gitconfig
├── dot_config/
│   ├── git/ignore                              → ~/.config/git/ignore
│   ├── ghostty/config.tmpl                     → ~/.config/ghostty/config
│   ├── zed/settings.json.tmpl                  → ~/.config/zed/settings.json (staged)
│   └── mise/config.toml.tmpl                   → ~/.config/mise/config.toml
├── private_dot_ssh/
│   └── config.tmpl                             → ~/.ssh/config (0600)
├── Library/Application Support/Code/User/
│   ├── settings.json.tmpl                      → VSCode user settings
│   └── keybindings.json.tmpl                   → VSCode keybindings
│
├── run_once_before_00-install-homebrew.sh.tmpl
├── run_onchange_10-install-packages.sh.tmpl    brew bundle from packages.yaml
├── run_onchange_15-vscode-extensions.sh.tmpl   `code --install-extension` per entry
├── run_onchange_18-mas-apps.sh.tmpl            `mas install` per entry (Magnet etc.)
├── run_once_20-1password-signin.sh.tmpl        interactive `op account add`
├── run_onchange_30-ssh-keys.sh.tmpl            `op read` → ~/.ssh keys
├── run_once_40-gh-auth.sh.tmpl                 `gh auth login` with token from op
├── run_onchange_50-mise-tools.sh.tmpl          `mise install` against mise.yaml
├── run_onchange_55-npm-globals.sh.tmpl         claude-code, gemini-cli, etc.
├── run_once_60-gcloud-init.sh.tmpl             interactive `gcloud auth login`
├── run_onchange_70-claude-mcps.sh.tmpl         register MCP servers
├── run_onchange_80-clone-repos.sh.tmpl         clone missing OVO repos
└── run_once_90-macos-defaults.sh.tmpl          `defaults write` (key repeat, Dock, etc.)
```

### Run mode semantics

- **`run_once_*`** — chezmoi executes exactly once per machine (state tracked by hash). Used for things that don't need to keep up with config drift (Xcode CLT, gcloud first auth).
- **`run_onchange_*`** — chezmoi re-executes when the rendered content's hash changes. Used for declarative inventories: edit `packages.yaml` → `chezmoi apply` re-runs the install. This is how the package list, MCPs, mise tools, and repo list stay in sync.

### Data files

`.chezmoidata/*.yaml` is auto-loaded by chezmoi into the template context. Example shape for `packages.yaml`:

```yaml
brew:
  formulae:
    common: [jq, ripgrep, fzf, tree, gh, mise, sf, 1password-cli, gnupg, mas]
    work:   []
    home:   []
  casks:
    common: [ghostty, visual-studio-code, docker, 1password, raycast]
    work:   []
    home:   [zed]

mas:
  common:
    - { id: 441258766, name: Magnet }

npm:
  globals:
    - "@anthropic-ai/claude-code"
    - "@google/gemini-cli"
```

A script then iterates the data with a small template:

```bash
# run_onchange_10-install-packages.sh.tmpl
brew bundle --no-lock --file=- <<EOF
{{- range .packages.brew.formulae.common }}
brew "{{ . }}"
{{- end }}
{{- range (index .packages.brew.formulae .machine) }}
brew "{{ . }}"
{{- end }}
{{- range .packages.brew.casks.common }}
cask "{{ . }}"
{{- end }}
{{- range (index .packages.brew.casks .machine) }}
cask "{{ . }}"
{{- end }}
EOF
```

### Bootstrap order

```
00  install-homebrew           no secrets
10  install-packages           installs op, ghostty, vscode, mas, etc.
15  vscode-extensions          uses `code` CLI from step 10
18  mas-apps                   Magnet (prereq: signed into App Store app)
20  1password-signin           INTERACTIVE — gates everything below
30  ssh-keys                   op read → ~/.ssh/*
40  gh-auth                    op read token, pipe to `gh auth login`
50  mise-tools                 no secrets — provides node for step 55
55  npm-globals                installs claude-code, gemini-cli (npm -g)
60  gcloud-init                INTERACTIVE — browser auth
70  claude-mcps                config-only — depends on `claude` CLI from step 55
80  clone-repos                uses SSH key from step 30
90  macos-defaults             `defaults write`
```

Steps 20 and 60 are the only interactive ones beyond the App Store sign-in prerequisite.

### Secrets handling

The rule: **no `onepasswordRead` template calls inside dotfile templates.** All secret reads happen inside `run_*` scripts via `op read` at execution time.

Two reasons:

1. **Bootstrap ordering.** Template rendering happens before any script runs. A `dot_gitconfig.tmpl` calling `onepasswordRead` would fail the very first apply because 1Password isn't signed in yet.
2. **Blast radius.** Keeping secret values out of rendered template content means they only exist in process memory when `op read` runs, never on disk except in their final target file (e.g., `~/.ssh/id_ed25519`).

Non-secret per-machine values (git email, signing key ID) flow through `.chezmoidata` or chezmoi's prompts — plain templating, no `op`.

### Machine variance

A single source of truth: `~/.config/chezmoi/chezmoi.toml`, generated by `.chezmoi.toml.tmpl` on init. Sets `{{ .machine }}` to `work` or `home`. Used by:

- `.chezmoidata/*.yaml` files for per-machine entries (e.g. `(index .packages.brew.casks .machine)`).
- Dotfile templates that need per-machine values (work email vs personal email in `.gitconfig`).
- The handful of scripts that need conditional logic.

## Operational workflows

### Fresh machine

```bash
# Manual prerequisites (one time):
# 1. Sign into the Mac App Store app.
# 2. Have your 1Password account credentials ready.

sh -c "$(curl -fsSL get.chezmoi.io)" -- init --apply <handle>/dotfiles
```

chezmoi installs itself, clones the repo, prompts for machine type, and walks the scripts in order. Steps 20 (1Password sign-in) and 60 (gcloud) prompt interactively. Everything else runs unattended.

### Day-to-day edit

```bash
chezmoi edit ~/.zshrc          # opens source in $EDITOR
chezmoi diff                   # preview
chezmoi apply
git -C ~/.local/share/chezmoi commit -am "tweak zshrc"
git push
```

### Sync from the other machine

```bash
chezmoi update                 # git pull + chezmoi apply
```

### Adding a new tool / extension / repo

Edit the relevant `.chezmoidata/*.yaml`, then `chezmoi apply`. The matching `run_onchange_*` script's rendered content changes, so chezmoi re-fires it.

## Idempotency contract

Every script is safe to re-run. Specifically:

- `brew bundle` — idempotent by design.
- `mas install <id>` — no-op if already installed.
- `code --install-extension <id>` — no-op if installed.
- `npm install -g <pkg>` — no-op if installed at the same version; upgrades in place otherwise.
- SSH keys — guarded with `[[ ! -f ... ]]`; never overwrites existing keys.
- MCP registration — re-issues against the canonical list (`claude mcp add` is idempotent).
- Repo clones — clone iff directory missing; no auto-pull of existing repos.
- `defaults write` — naturally idempotent.

## Failure mode and recovery

Every script header:

```bash
set -euo pipefail
trap 'echo "FAILED at line $LINENO in $(basename "$0")" >&2' ERR
```

chezmoi halts the chain on the first non-zero exit. The failed script's hash is **not** recorded in state, so `chezmoi apply` resumes from that step.

Escape hatches:

| Need | Command |
|---|---|
| Preview changes | `chezmoi diff` |
| Render dry-run (no scripts) | `chezmoi apply --dry-run` |
| Skip scripts this run | `chezmoi apply --exclude=scripts` |
| Force re-run a `run_once_*` | `chezmoi state delete-bucket --bucket=scriptState` |
| Inspect state | `chezmoi state dump` |
| Verbose narration | `chezmoi apply --verbose` |

## Testing strategy

Three escalating levels matched to risk:

| Risk | Approach |
|---|---|
| Dotfile edit | `chezmoi diff` then apply; revert + reapply if wrong. |
| New `run_once_*` script | Reset its state bucket, apply with `--verbose`. |
| New `run_onchange_*` that mutates system | Run in a scratch macOS user account (documented in README). |

Static checks via pre-commit:

- `shellcheck` over all `.sh` and `.sh.tmpl` files.
- `chezmoi execute-template` rendering pass to catch template errors before commit.

No GitHub Actions CI: macOS runners don't usefully validate the "second-run" case that `run_onchange_*` exists for, and the cost/value isn't there for a personal tool.

## Manual follow-ups (cannot be automated)

Documented in the repo's README:

1. Sign into the Mac App Store app (required for `mas install`).
2. 1Password sign-in (`op account add`) — interactive password / hardware key.
3. `gcloud auth login` — browser SSO.
4. `gh auth login` — pulls token from 1Password but may need 2FA prompt.
5. Salesforce CLI org auth (`sf org login web`) — browser SSO, only on the machine doing Salesforce work.
6. Generate or import GPG signing keys if used (or pull from 1Password).
7. macOS Settings panes that aren't reachable via `defaults write` (e.g., Accessibility permission grants for tools like Raycast/Magnet).

## Open questions for the implementation plan

- Exact contents of `.chezmoidata/*.yaml` need to be enumerated from the current home machine (running inventory: brew, casks, mas, code extensions, mise tools, MCP servers, OVO repos).
- Specific 1Password item paths (e.g., `op://Personal/SSH ed25519/private-key`) need to be agreed and the items created if absent.
- Whether `dot_zshrc.tmpl` is a single file or sources modular fragments from `dot_config/zsh/*.zsh`.
- Whether to enable chezmoi's auto-commit/auto-push for `chezmoi edit` (convenience vs. lost review opportunity).
- Verify exact npm package names for Gemini CLI (`@google/gemini-cli` is the assumed upstream).
